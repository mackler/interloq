# Interloq

A TypeScript program ("the orchestrator") that runs Claude Code and Codex against one project.
Claude Code writes a plan, Codex reviews it in rounds until a review contains no counted issue,
Claude Code implements the plan, Codex reviews the work after every execution phase, and every
stop or accepted work issue leads to a plan revision and a new review before work continues.
The user follows and answers in a web page (`src/web.ts`); the terminal interface was removed (issue #88, by the developer's decision of 4 Oct 2026). The orchestrator contains no model calls of its own; it
starts both agents through their SDKs, passes text between them, keeps the records, and asks the
user for a decision at defined points. It is written with the Effect library (v4): the procedure
is one Effect program over six services (the sixth, `Decider`, runs the decision loops of decision support), and the edges (files, git, terminal, SDKs) are layers.

## Commands

- `npm run check` — type check: `node scripts/check.ts` (issue #105) runs three checks at the same time: `check:program` (`tsc --noEmit`: the program, tests, prototypes), `check:web` (`tsc --noEmit -p web`: the browser code under `web/src`) and `check:svelte` (`svelte-check`: the `.svelte` components). Each check's output is printed whole when it ends, a failure of one does not stop the others, and the exit code is 1 if any failed. Must report nothing before every commit; `.githooks/pre-commit` runs it and refuses the commit otherwise. Enable the hook once per clone with `git config core.hooksPath .githooks`. Because the hook runs it, do not run it yourself before committing: commit, and let the hook check (issue #77). Run it by hand only to find type errors while working. The two `tsc` passes are incremental, their build info under `scratch/tsbuildinfo/` (excluded from the project snapshot by `ignorePaths` and ignored by git; `test/buildInfo.test.ts`); `svelte-check` has no incremental mode.
- `npm run build` — builds the page with Vite into `web/dist/` (git-ignored); the web server refuses to start without it.
- `npm run test:unit` (`node --test test/*.test.ts`), `npm run test:web` (Vitest over `web/src/**/*.test.ts`, jsdom), `npm run test:e2e` (Playwright against the server over scripted agents; `E2E_SCENARIOS=tabs npx playwright test e2e/run.spec.ts -g '\(7\)'` starts only the named scenario servers, so that one test runs in a short command; `-g` is a regular expression, so the parentheses are escaped and the pattern single-quoted: the unescaped `-g "(7)"` also selects `(7a)` and `(17)`, and `(17)`'s server (`transportRetry`) is not started), `npm run test:cli` (`bats test/cli`: `bin/ilcli` over temporary git repositories, with `docker` and `npm` replaced by the stubs in `test/cli/stubs/`).
- `npm run generate:cli` — regenerates `bin/ilcli` from `bin/ilcli.bashly/` with bashly (2.0.0, provided by the container image; the host has none, so the generated script is committed). Run it after every change of `bin/ilcli.bashly/`; `test/cli/generated.bats` fails until the committed script is what bashly generates.
- `npm test` — `node scripts/test-all.ts` (issue #75): the type check, `npm run test:unit`, `npm run test:cli`, `npm run test:web` and `npm run build` run at the same time, each stage's output printed whole when it ends, then `npm run test:e2e` if all of them passed — scenario tests with scripted agents, the adapters over a fake SDK, the store on a temporary git repository, and `test/deps.test.ts`, which checks that the pinned versions are installed. A type error fails `npm test`, and the end-to-end tests do not start. The end-to-end tests run in parallel on half of the machine's cores (`workers: "50%"`, set in `playwright.config.ts` alone and checked by `test/ci.test.ts`). No credentials needed; requires `git`. The tools these need beyond npm — Playwright's Chromium, bashly (2.0.0) and bats (1.11.1) — all come from `container/Dockerfile`, so a container built from it needs no manual installation. A container built before 27 Sep 2026 lacks bats, and `npm test` then fails at `test:cli`: rebuild with `bin/ilcli build`, `down` and `shell`.
- Real run, inside a project container that has both agents' credentials and network access: `node /opt/interloq/src/web.ts [port]` (default 8090; needs `npm run build` first, so every run needs the page built), then open the page and start tasks there. The page is the program's only user interface (issue #88).
- `bin/ilcli release` — on the host, in the development clone: pushes `main` to GitHub (refuses on uncommitted changes, another branch, or a `main` behind `origin/main`). `bin/ilcli upgrade` — on the host, in the installed copy: fetches `release`, fast-forwards, then `npm ci` and `npm run build` every time. `bin/ilcli help` documents every command.

The program itself has no build step: Node.js (22.18 or later) runs the `.ts` files directly by removing the types. The page is built (`npm run build`), and the server refuses to start without it, so every run needs it.

The minimum, Node.js 22.18, is enforced: `package.json` declares `engines` `>=22.18` and `.npmrc` sets `engine-strict=true`, so `npm ci` refuses an older Node. `.node-version` holds the exact Node version of the container image (26.10.0 on 27 Sep 2026), which the CI workflow uses; update it whenever the image's Node changes — `test/deps.test.ts` fails until it matches the running Node.

## TypeScript constraints (required by direct execution)

- Erasable syntax only: no `enum`, no parameter properties, no namespaces with runtime code (`erasableSyntaxOnly` enforces this). Effect's tagged error classes (`class X extends Data.TaggedError("X")<{…}> {}`), service classes (`Context.Service<X, Shape>()("key")`) and generator functions (`Effect.gen`) are erasable and are used.
- Type-only imports use `import type` (or inline `type`); Node.js does not remove unused value imports.
- Relative imports carry the `.ts` extension.
- Node.js does not type check. `npm run check` is the only type check.
- Every Effect and `@effect/platform-node` name used in the program is recorded in `docs/effect-v4-api.md` with the file and line of its declaration in `node_modules`. Look a name up there, or read the `.d.ts` file and add it, before using it. Material online describes v3 in most cases and is not a source.

## Programming principles

The program follows functional programming: pure functions everywhere except at the edges, which are
identified as such (the layers of `src/store.ts`, `src/webUi.ts`, `src/claude.ts`, `src/codex.ts`, and the
untested wiring); no exception is thrown — a failure is a typed error in the `Result` or the error
channel of an Effect, and a defect is a bug; data are immutable algebraic data types (readonly records,
tagged unions, `Result`, `Option`), never mutated after construction; recursion instead of iteration
where it is stack safe (`Effect.gen` and Effect's own combinators are, plain recursion over
unbounded input is not); effects are values, composed and run at the edge; and the rest that goes
with it: no shared mutable state, no `null`-or-throw signatures, no hidden preconditions,
exhaustiveness over variants, and a pure core that the tests exercise directly. The findings and
recommendations of `docs/functional-design-review.md` are the reference for what this means here.

A type admits exactly the values the domain has. Where the presence, meaning or legality of one field
depends on another field's value, the type is a tagged union of the cases, not a record with a flag;
fields that cannot vary independently are one field. A validation rule that rejects a *combination*
of fields is evidence that the type is wrong — make the combination unrepresentable rather than check
for it. The same holds for a check on a value's own content: a string that must not be blank, a
number within a range, a path already resolved, a text of one line. The value gets a type whose only
inhabitants satisfy the rule, built by a function that returns a `Result`, so that an invalid value
cannot be constructed rather than being rejected after it exists; `ProjectPath` and `RecordPath`
(`src/services.ts:87`) are the pattern already in use. What stays a check is what no constructor can
decide: a comparison of a value with something outside it, such as a reply against what the program
supplied, and a judgment of prose that only a reviewer can make. At the agent
boundary a union becomes an `anyOf` of closed objects in the JSON Schema, which both agents accept:
the `Block` union of issue #36 went to Codex and to Claude Code in both variants on 6 Oct 2026, the
strict one with its `$ref`s inlined, and all were accepted (see the facts below). A new union there
is therefore ordinary, and the prototype run proves it again whenever the schemas change.

## Behaviour that is decided and must not change without the developer's instruction

1. The program waits for the user only where a decision is required. No confirmation prompts elsewhere, with one exception (issue #25, 29 Sep 2026): every answer that ends the run is confirmed first. This covers End the run (`q` at a one-line prompt, `/quit` in a message, the page's button), Stop task in the page, and at the cycle limit every answer that stops the run (`0`, an empty answer, anything that is neither an offered `p` nor a count; `limitStops` in `src/input.ts`), clicked or typed. The page decides by one predicate, `endingOf` in `src/input.ts`, and opens `ConfirmEndDialog`. Only the dialog's confirming button ends the run; anything else returns to the question. The confirmation says what ends, that the records in `plan-review/` remain, and the exit code the program then returns. Ctrl+C in the server's terminal ends the server and asks nothing.
2. Question phase before planning phase 1: Claude Code proposes a question list (question, reason, proposed answers, default); Codex reviews it; the interview takes place in the web page; follow-up questions are unrestricted; Claude Code proposes the end with a summary and the user confirms; Codex reviews `requirements.md` for gaps, and accepted gaps lead to a second interview. Since the task of issues #46, #59, #34, #36, #25, #20, #19, #57 and #58 (29 Sep 2026), every question put to the user follows one statement of the rules, `QUESTION_RULES` in `src/prompts.ts`. The writer's prompts carry `questionWritingRules()` and the reviewers' carry `questionReviewCriteria()`; `validateQuestion` in `src/question.ts` checks their mechanical part, with the validation repair turn of behavior 10. Every question entry carries a context paragraph. After the question review converges, a fresh session writes the explanations of the agreed questions' terms (`terms.json`), which Codex reviews in a loop of their own (the terms subject, ids `T-R<n>-<i>`) before the clarification; an empty agreed list skips it. Since the task of issues #36, #59 and #66 (30 Sep 2026), a question's text is a sequence of pieces and its explanations a list the pieces refer to by id: the list's writer writes plain pieces only, and the session that writes the explanations returns each agreed question divided into pieces that refer to them, its wording unchanged (decision Q1; `KEEP_WORDING`, checked by `termsValidation`). The context and the details are blocks: paragraphs, bulleted lists with levels, and code blocks, whose kind is data (decision Q2); a plain piece is inline Markdown only: emphasis and links, never code. Every backtick in a plain piece is shown as a backtick character, and a literal value is its own code piece (the developer's decision of 4 Oct 2026, the last step of the task of issues #36, #59 and #66; `plainMarkdown` in `src/pieces.ts`, the clause `inline` of `QUESTION_FORMAT`). A plain piece never opens a block either: `plainMarkdown` writes what would open one at the start of a line as its characters (issue #94, 5 Oct 2026). Nothing reads Markdown to find a term: the validation is checks on data (`QUESTION_FORMAT`). An agreed question is presented from `questions.json` and `terms.json` alone, whatever the turn writes beside its id. Any other question an interview turn asks (a follow-up, an accepted gap in the second interview) is written in full in `current_question` and validated, with no Codex review (decision Q12). Every question, whatever produced it, reaches the user through `askOffering` in `src/offer.ts` as one `QuestionPresented` event: numbered in one sequence for the run, with where it came from, its context paragraph, what it is about (a pause's facts as prose, never JSON; the summary to confirm; a permission's tool input, each field named and explained), its terms, and its options with the answer that chooses each. A question the program composes (a pause of behavior 7, the cycle limit, the unchanged pause, the transport pause for Codex, a permission request) gets its context and terms from a context call, which since 30 Sep 2026 returns the whole question as pieces: it may rephrase the question, the options and the prose of the details, keeps every option in its position, every literal value exactly (decision F1) and every reference the program supplied (decision G-R1-1 of that task). That call runs in a fresh session with the capability `readProject` (behavior 3); it is skipped for the transport pause of Claude Code, and when it cannot succeed the program's fixed paragraph is shown instead, marked as the program's (decisions Q1 and G-R1-1). An entry of the question list may name another entry and one of its proposed answers that make it unnecessary (`skip_if`, issue #99, by the developer's task of 6 Oct 2026): the program checks the condition with the validation repair turn of behavior 10, records the list so that the question follows the one it names, and during the clarification does not ask a question whose premise the user's answer denied, says so to the user and in `conversation.md`, and counts "x of N answered" over the questions that remain; `requirements.md` lists such a question under 'Skipped questions'.
3. Planning calls: Claude Code may write only under `plan-review/`. A `PreToolUse` hook denies other edits before they occur; the project snapshot comparison after each call is the second check. A third capability, `readProject` (S33, 29 Sep 2026), is that of the context call of a question: a `PreToolUse` hook without a matcher lets Read, Grep, Glob and the structured output through and denies every other tool, and like `readOnly` it has the records guard (a changed guarded record halts with `RecordsChanged`, which the context call's fallback does not catch). Claude Code writes no plan file (issue #6, decision F1, 28 Sep 2026): every call that creates or changes the plan (the plan write, the response to a plan review, the application of the user's decisions) returns the whole plan as data (`PlanWrite`, `PlanResponse`), the program validates it (`validatePlan` in `src/plan.ts`: unique step ids; a step that is `done` keeps its id, label and text; a failure gets the validation repair turn of behavior 10) and writes `plan.json` and `plan.md`. The hook denies an edit of either file, in planning and in execution.
4. Execution phases use `permissionMode: "auto"`. A call to `AskUserQuestion` is a stop: the answer is recorded, a hook then denies every tool except `StructuredOutput`, the turn ends, and the plan is always revised and reviewed before the next execution phase. An execution call offers the in-process tool `report_step(id, "started" | "done")` (issue #6, Q2; `createSdkMcpServer` in `src/sdkLive.ts`), allowed without a prompt and denied after a stop like every other tool; `executePrompt` requires it when a step begins and when it is done. The program records each report on the plan it loaded when the phase began (`src/planSteps.ts`), writes `plan.json` and `plan.md` and notifies the page at once; an id not in the plan is an error for Claude Code and changes nothing. When the call ends, however it ends, a step still `started` becomes `unfinished`, and the held plan is written again. `executePrompt` lets Claude Code work the steps in any order with one step open at a time, and asks for a resumed step to be reported `started` again; nothing is refused on that ground (issue #53, by the developer's decision of 29 Sep 2026). A call that fails from a transport fault (behavior 14) is resumed in the same session with `executionContinuePrompt`, with the same hooks, stop and `report_step` server, so the end handling runs once, when the call finally ends; a recorded stop, or a valid status report delivered before the fault, ends the call without a retry (issue #26, by the developer's instruction of 29 Sep 2026). A question Claude Code relays with `AskUserQuestion` carries its context and explanations in its text, in the shape `executePrompt` states (`RELAYED_SHAPE`: since 30 Sep 2026 one JSON object with the context, the question, the explanations and the tool's options as pieces, in the tool's order; decision G-R1-2), which `parseRelayedQuestion` in `src/question.ts` decodes; the answer returned to Claude Code is the tool's own label. A text without that shape is not denied: a context call writes its context and terms from the question, the task and `plan.md` while the execution call waits (decision Q2). The stop is unchanged. A permission request shows the tool's input field by field: a known field under a plain label (`TOOL_INPUT_LABELS`), and any other field under its own name, shown as code on one line with its line breaks and hidden characters escaped, and explained as a term (the label table is looked up by its own entries only; S55). A name with a backslash, a line break or a hidden character, or made of whitespace alone, is shown with visible escapes (its backslashes doubled, a space as `\u0020`) and the escapes' note; an empty name has a fixed label and no term; so distinct names never look alike (S57). A multi-line value is a code block, followed by the escapes' note where it needs one; both are shown inside the item of their setting, and the settings after them keep their nesting (`normalizedRuns` in `src/pieces.ts`, the clause `interrupted` of `QUESTION_FORMAT`; W2-R1-1). Every text value and every number is shown literally, as code (`codeSpan` and `codeFence` in `src/prompts.ts`; S45; a number since work review 1 of 30 Sep 2026). The empty text is a fixed phrase, and a value of whitespace alone is named as its runs in order. An empty list, an empty object and an input with no settings are named by fixed phrases as plain text (`EMPTY_LIST_PHRASE`, `EMPTY_OBJECT_PHRASE`, `NO_INPUT_PHRASE`; S60), and so are a boolean and null (`YES_PHRASE`, `NO_PHRASE`, `NONE_PHRASE`: `(yes)`, `(no)`, `(none)`). A context call that rephrases the question keeps every value, as code or as phrase, in its order, and adds none; a value of several lines stays a code block, since a code piece holds one line (the clause `codeLine` of `QUESTION_FORMAT`, W3-R1-1); and a reference Interloq supplied on a setting's name stays on that name, on every occurrence of it and in no other part of the question (`KEEP_SUPPLIED_REFS`, W4-R1-1, P5-R1-1); two code pieces never stand next to each other (the clause `codeAdjacent`, W5-R1-1) (`KEEP_LITERALS`; `valueTokensOf` in `src/pieces.ts` over `valuePhraseAt` in `src/prompts.ts`, which recognizes every phrase the program can write; W1-R1-1). A character that a code span or the browser would change or hide (a carriage return, a control or zero-width character, a special space at an edge) is written as a visible escape, with a note saying what the escapes stand for (`shownValue`, `ESCAPED_VALUE_NOTE`; S48); so is a line break at the start or end of a multi-line value (S54). The page keeps that whitespace when it renders the value: one rule in `web/src/theme.css` sets code in rendered Markdown to `white-space: break-spaces` with a tab size of 4, inline code as an inline block, and code blocks to `pre` (S51). The question names the action and points at the input shown above it, never containing the input itself (`permissionQuestion`, `permissionDraft` in `src/offer.ts`; S49).

14. Transport retry (issue #26, by the developer's instruction of 29 Sep 2026). A failure of an agent call is classified in `src/transport.ts`, the one place that inspects an SDK's failure: only positive transport evidence belonging to the failure (a dropped connection, a reset, a timeout, an HTTP 5xx: a terminal fact of the call, or evidence with no progress after it) makes it a `TransportFault`, and known permanent evidence (a 4xx, a usage or rate limit, a permanent assistant error, a stopping result subtype, including those of the SDK's own `api_retry` messages) wins; anything unrecognized is not retried. `TransportFault` is not a `RunError`. Codex turns and planning calls are retried by their callers in `src/review.ts`, execution calls inside `src/claude.ts`, which alone holds the call's session, stop and reporter; `Planner.executing` declares no `TransportFault`. Each retry waits `transportRetryDelaySeconds × 2^(k-1)` (behavior 9), is notified (`TransportRetrying`), said to the page and written to `conversation.md`, and shown on the page's activity line as a count of attempts, with a determinate indicator and the time remaining that count the wait down while the program waits (issue #63, by the developer's task of 7 Oct 2026; until then an indeterminate indicator). The guards of behaviors 3 and 5 take their baselines once per call and compare after every attempt, failed ones included, and before every retry; the records guard of a read-only call replays the Store's journal of its own writes, each with its preimage (`compareJournaled`), so the program's writes during a wait pass and an external change before or after one of them halts with `RecordsChanged`. When the retries are exhausted the run pauses; its question names the agent and the call, and the attempts and the last fault are in its details, the fault shown literally as code (`transportDetails`; S52): Retry again (another full set, the waits starting again) or Stop, with decision support's offer; Stop halts with `AgentUnreachable`, naming the agent, the attempts and the last fault. A Codex `error` event is a notice of the CLI's reconnection (`AgentReconnecting`), not a failure: a turn fails on `turn.failed`, on a stream that ends without `turn.completed`, or without an agent message. A Claude Code result of subtype `success` with `is_error` is a failure, so it never reaches the decoding and spends no repair turn; the SDK's own `api_retry` messages are notified.

The program waits on the Clock until the stated instant plus one minute; it says the wait and its end and records both in `conversation.md`; it writes the wait to `usage.jsonl` as actually spent, an interrupted wait included, and the summary printed at the end names it; the page shows it on the activity line with a determinate indicator and the time remaining. The guards of behaviors 3 and 5 hold across the wait as they do across a backoff, and the transport retries are untouched by it. A limit without a stated reset stays permanent: a planning call fails with `ClaudeCallFailed`, and an execution call ends `aborted` and the user is asked, as before. Codex's limits are unchanged. A wait holds the container, the web server and the agent's session open for its whole duration, up to a week for a weekly limit, and a machine that sleeps or a container that restarts ends the run, which cannot be resumed (issue #4).

## User interface

Adherence to Jakob Nielsen's ten usability heuristics is a top priority for every user interface of
this program, which since issue #88 is the web page alone: visibility of system status; match between the
system and the real world; user control and freedom; consistency and standards; error prevention;
recognition rather than recall; flexibility and efficiency of use; aesthetic and minimalist design;
help users recognize, diagnose, and recover from errors; help and documentation. A design decision
about the interface is argued from these heuristics, and a review of the interface checks against them.
The visual design follows Material Design (Google's design system, m3.material.io): its components,
layout, typography, colour roles, elevation, motion and states. A component library that implements it
is a dependency and needs the developer's instruction like any other; without one, the guidelines are
followed by hand.
Where the library has no component for what the guidelines specify, a substitute may be used only if
it asserts nothing the specified component does not. A substitute that claims more — a determinate
indicator in place of an indeterminate one, a progress figure in place of a busy state, a count in
place of an estimate — is not a deviation but a different statement, and the guidelines are followed
by hand instead. A deviation recorded in `docs/ui-review.md` states what the substitute asserts, not
only that it was substituted. No test can catch this: a rendered element is asserted to be present,
never to be truthful (issues #42 and #43).

A run that waits for the user, or a run he watched that has ended, is announced to a user who is not looking at the page
(issue #16). The tab's title marker and the icon's badge assert that a prompt is pending, or that a run this page
watched ended while the tab was hidden and has not been seen since, and nothing more; they are always on and are not a
preference. A desktop notification asserts the same, once per prompt and once per end; it is opt-in and revocable from
the page's switch, and needs the browser's permission, asked from that switch's click alone. A sound is a separate
opt-in, off by default. Neither fires at a visible tab showing the prompt, and every tab of a run fires, since either
may be the one the user cannot see. The decision is `decide` in `web/src/notify.ts`.

Command-line behaviour follows the Command Line Interface Guidelines (clig.dev): the developer's
command `bin/ilcli` and the command line of `src/web.ts` (`src/webArgs.ts`). It
governs the command line only — the page answers to the heuristics and to Material Design above, and
the program's internals to the Programming principles. Several of its points are already decided
behaviour and stay as they are: configuration precedence (behaviour 9), the exit codes (behaviour 11:
130 interrupted, 1 halted, as the recorded end of a run), and prompting the user only where a decision is
required (behaviour 1). Where it adds something, it is the standard a command-line decision is argued
from, as the heuristics are for the interfaces.

## Rules for changes

- The type first. Before the test, the data types and the signatures the change needs are written and settled: a change of behaviour states what its types become before anything else is written, and a plan's step says so in its text. The test is then written against them, and a type error naming a signature is the ordinary way it first fails. The types are not the application code the next rule speaks of; writing them is the first act of a change, not an exception to it.
- Test first, without exception. Before application code is written or changed, the test that specifies it is written, run, and seen to fail for the reason the change is meant to fix (a failed assertion, or a type error naming the signature being changed; never a missing module or a typo). Then the least code that makes it pass. A new module may first be scaffolded with its final signature and a body that does nothing useful, so that the test fails on its assertion. The observed failure is recorded in the commit message.
- Then refactor, which is the third step and not an optional one. "The least code that makes it pass" is licensed to be crude only because this step removes the crudeness: without it a change leaves behind what the green step was permitted to write. Improve the code against the Programming principles — a type that admits more values than the domain has, a check on a value's own content where a constructor returning a `Result` was called for, a function doing two things, duplication, a name that described the first version. **No test changes**: the tests of the step and the suites the change touches are re-run unchanged and must still pass, which is what makes it refactoring rather than a change of behaviour; a test that has to change is evidence that behaviour changed and belongs in a step of its own. Nothing is added that no test covers. The step's record says what was improved, or that nothing needed it.
- Property-based testing wherever it applies (issue #66). Where a function is pure and an invariant can be stated over arbitrary input, a property test with `fast-check` states it: the modules the Layout table marks pure are where they belong. Example tests remain for what properties do not cover: a specific case that once failed, a value a seam must agree on exactly, and the scenario tests required for every change of behaviour; the two are not alternatives, and a property over a pure function is no substitute for a scenario test. A property test is written first and seen to fail, like any other. Its case count is chosen so that `npm test` stays usable before every commit and in CI.
- Every change to behaviour gets a scenario test in `test/` that runs the procedure against the test layers of `test/helpers.ts` (`testLayer`, `testWiring`). `src/issueLog.ts` stays free of I/O and of Effect services so that it can be tested directly.
- Test the seams, not only the sides. Where two modules must agree on a value — a label, a format, a path, an identifier — a test asserts their agreement directly, by deriving both sides from one source in the test and comparing them. Testing each side against a literal of its own is not enough: it passes while they disagree. The same applies where one module produces text that another parses, and where a claim in a structured reply is meant to correspond to a change on disk. Two runs were lost in one day to seams of exactly this kind (issues #30 and #37), each with both sides tested and neither with a test of the agreement between them.
- A prompt that tells an agent what value to return, and the validation that checks the returned value, are written and changed together, and one test exercises both.
- `src/claude.ts` and `src/codex.ts` receive the SDKs through the `Sdk` service and are tested with `test/fakeSdk.ts`. Only `src/sdkLive.ts` (the binding) and `src/web.ts` (the wiring and the runner) are untested. Their text is no longer shown to the developer before it is written (his decision of 7 Oct 2026): the two hold 96 lines of wiring with no logic, the hook type checks them, and the work review reads them in the diff like every other file, while showing them cost a stop and, with it, a planning call, a review loop and a work review every time (issue #90). No scaffolding may reach a real agent: a scaffold of an adapter makes the SDK call impossible. Verify SDK option names against the type declarations in `node_modules`, not from memory.
- Do not add a dependency without the developer's instruction. Permitted besides the two SDKs: `effect`, `@effect/platform-node`, and these devDependencies, each pinned exactly and checked by `test/deps.test.ts`: `fast-check` (property tests); for the web GUI (instructed 26 Sep 2026) `svelte` (the page), `vite` and `@sveltejs/vite-plugin-svelte` (the build), `vitest` (component tests), `jsdom` (the DOM for Vitest), `svelte-check` (type check of `.svelte` files), `@playwright/test` (end-to-end tests), `marked` and `dompurify` (Markdown rendering and sanitising in the page), `m3-svelte` (Material Design 3 components) and `vite-plugin-functions-mixins` (the CSS `@function`/`@mixin` of m3-svelte's components, resolved at build time). A runtime dependency, permitted on the developer's instruction of 28 Sep 2026: `zod` (4.6.5, the Agent SDK's peer dependency), because the SDK's `tool()` takes the input of `report_step` only as a zod shape; it is imported by `src/sdkLive.ts` alone (and by the prototype `prototypes/proto.ts`), which `test/deps.test.ts` checks with its pin. Outside npm, two tools of the container image, neither an npm dependency: bashly (generates `bin/ilcli`) and bats (its tests; permitted on the developer's instruction, 27 Sep 2026; meant to come from the image, installed by hand until then).
- This directory is the development clone. The installed program is `~/work/interloq` on the host, which project containers mount read-only at `/opt/interloq`, and it tracks the branch `release` of github.com/mackler/interloq, not `main`. A change reaches real runs by one route: the developer runs `bin/ilcli release` (pushes `main`); the workflow `.github/workflows/ci.yml` runs `npm test` on GitHub; only if it passes does its `release` job fast-forward `release` to that commit (with a deploy key, the only identity a ruleset lets update `release`); then `bin/ilcli upgrade` on the host brings the installed copy to `origin/release` and runs `npm ci` and `npm run build`. So the installed copy can only ever pull a commit whose suite has passed — the point of the route. Nothing in this container can push, reach GitHub Actions, or touch `~/work`; the developer does those steps.
- `bin/ilcli` starts the development container (`compose.cc.yaml`) and carries a change to the installed copy (`release`, `upgrade`); it is not part of the program. It is generated by bashly from `bin/ilcli.bashly/` and tested by `test/cli/*.bats`.

## Credentials in the development container

`CLAUDE_CODE_OAUTH_TOKEN` is Claude Code's login, and Codex's credentials come from the `~/.codex`
volume; both are needed for a run. `INTERLOQ_ISSUES_TOKEN`, added 27 Sep 2026, is optional and is
**not** used by the program: it is a fine-grained GitHub token limited to this repository with Issues
read and write, which lets the assistant working in the container file an issue with the REST API.
Reading issues needs no token, because the repository is public. Nothing in `src/` may read any of
these, and no prompt, record or log may contain one; every process in the container can read the
environment, so the token's scope is the safeguard, not its secrecy.
