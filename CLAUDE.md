# Interloq

A TypeScript program ("the orchestrator") that runs Claude Code and Codex against one project.
Claude Code writes a plan, Codex reviews it in rounds until a review contains no counted issue,
Claude Code implements the plan, Codex reviews the work after every execution phase, and every
stop or accepted work issue leads to a plan revision and a new review before work continues.
The user follows and answers in a web page (`src/web.ts`); the terminal interface was removed (issue #88, by the developer's decision of 4 Oct 2026). A run is one of two modes, each started from an item of the project's issue tracker in the page's tab of that mode (issue #120, the developer's decision of 8 Oct 2026 in issue #120): a refinement run is the question phase alone, whose `requirements.md` is written back to the item, which becomes `refined`; an implementation run is the planning, execution and review, its item `implementing` at its start and `implemented` when it finishes. One run of each mode may be in progress at once. The orchestrator contains no model calls of its own; it
starts both agents through their SDKs, passes text between them, keeps the records, and asks the
user for a decision at defined points. It also reads and writes the project's issue tracker (issue #120): the first
network edge it owns, the call always made by Interloq and never by an agent, since a planning call cannot reach the
network. The tracker is the `Tracker` port of `src/services.ts`, beside the services and not one of them: every run
reads its item and sets its state through it, and the decision loops and the review loop never use it. It is written with the Effect library (v4): the procedure
is one Effect program over seven services (`Decider` runs the decision loops of decision support, and `RunKind`, issue #120, carries the run's mode), and the edges (files, git, terminal, SDKs) are layers.

## Commands

- `npm run check` — type check: `node scripts/check.ts` (issue #105) runs three checks at the same time: `check:program` (`tsc --noEmit`: the program, tests, prototypes), `check:web` (`tsc --noEmit -p web`: the browser code under `web/src`) and `check:svelte` (`svelte-check`: the `.svelte` components). Each check's output is printed whole when it ends, a failure of one does not stop the others, and the exit code is 1 if any failed. Must report nothing before every commit; `.githooks/pre-commit` runs it and refuses the commit otherwise. Enable the hook once per clone with `git config core.hooksPath .githooks`. Because the hook runs it, do not run it yourself before committing: commit, and let the hook check (issue #77). Run it by hand only to find type errors while working. The two `tsc` passes are incremental, their build info under `scratch/tsbuildinfo/` (excluded from the project snapshot by `ignorePaths` and ignored by git; `test/buildInfo.test.ts`); `svelte-check` has no incremental mode.
- `npm run build` — builds the page with Vite into `web/dist/` (git-ignored); the web server refuses to start without it.
- `npm run test:unit` (`node --test test/*.test.ts`), `npm run test:web` (Vitest over `web/src/**/*.test.ts`, jsdom), `npm run test:e2e` (Playwright against the server over scripted agents; `E2E_SCENARIOS=tabs npx playwright test e2e/run.spec.ts -g '\(7\)'` starts only the named scenario servers, so that one test runs in a short command; `-g` is a regular expression, so the parentheses are escaped and the pattern single-quoted: the unescaped `-g "(7)"` also selects `(7a)` and `(17)`, and `(17)`'s server (`transportRetry`) is not started), `npm run test:cli` (`bats test/cli`: `bin/ilcli` over temporary git repositories, with `docker` and `npm` replaced by the stubs in `test/cli/stubs/`).
- `npm run generate:cli` — regenerates `bin/ilcli` from `bin/ilcli.bashly/` with bashly (2.0.0, provided by the container image; the host has none, so the generated script is committed). Run it after every change of `bin/ilcli.bashly/`; `test/cli/generated.bats` fails until the committed script is what bashly generates.
- `npm test` — `node scripts/test-all.ts` (issue #75): the type check, `npm run test:unit`, `npm run test:cli`, `npm run test:web` and `npm run build` run at the same time, each stage's output printed whole when it ends — scenario tests with scripted agents, the adapters over a fake SDK, the store on a temporary git repository, and `test/deps.test.ts`, which checks that the pinned versions are installed. A type error fails `npm test`. `npm test` does not run the end-to-end tests: they are `npm run test:e2e`, run by hand and by the CI workflow as a step of its own after `npm test` (the developer's decision of 19 Oct 2026, after the final suite run of issue #179's run passed every test it reached and was stopped at the 20-minute ceiling on a loaded machine). The end-to-end tests run in parallel on half of the machine's cores (`workers: "50%"`, set in `playwright.config.ts` alone and checked by `test/ci.test.ts`). The component tests (`npm run test:web`) likewise run on half the cores (`maxWorkers: "50%"`, set in `web/vite.config.ts` alone and checked by `test/ci.test.ts`), because Vitest waits a fixed 60 s for each worker to start. Their per-test timeout is 120 s (`testTimeout`, set in `web/vite.config.ts` alone and checked by `test/ci.test.ts`), because the longest property tests run past 30 s under that load. No credentials needed; requires `git`. The tools these need beyond npm — Playwright's Chromium, bashly (2.0.0) and bats (1.11.1) — all come from `container/Dockerfile`, so a container built from it needs no manual installation. A container built before 27 Sep 2026 lacks bats, and `npm test` then fails at `test:cli`: rebuild with `bin/ilcli build`, `down` and `shell`.
- Real run, inside a project container that has both agents' credentials and network access: `node /opt/interloq/src/web.ts [port]` (default 8090; needs `npm run build` first, so every run needs the page built), then open the page and start a run from an item in the tab of its mode (issue #120). The project's tracker must be named by `tracker` in `config.json` or `<project>/plan-review/config.json` (behavior 9), and the container must have its credential (`INTERLOQ_GITHUB_TOKEN`); without either, each tab shows a notice and no run starts. The page is the program's only user interface (issue #88).
- `bin/ilcli release` — on the host, in the development clone: pushes `main` to GitHub (refuses on uncommitted changes, another branch, or a `main` behind `origin/main`). `bin/ilcli upgrade` — on the host, in the installed copy: fetches `release`, fast-forwards, then `npm ci` and `npm run build` every time; it refuses while a running container that mounts the installed copy runs anything from it (issue #172), and `--force` skips that check (issue #104). `bin/ilcli help` documents every command.

The program itself has no build step: Node.js (22.18 or later) runs the `.ts` files directly by removing the types. The page is built (`npm run build`), and the server refuses to start without it, so every run needs it.

The minimum, Node.js 22.18, is enforced: `package.json` declares `engines` `>=22.18` and `.npmrc` sets `engine-strict=true`, so `npm ci` refuses an older Node. `.node-version` holds the exact Node version of the container image (26.10.0 on 27 Sep 2026), which the CI workflow uses; update it whenever the image's Node changes — `test/deps.test.ts` fails until it matches the running Node.

## TypeScript constraints (required by direct execution)

- Erasable syntax only: no `enum`, no parameter properties, no namespaces with runtime code (`erasableSyntaxOnly` enforces this). Effect's tagged error classes (`class X extends Data.TaggedError("X")<{…}> {}`), service classes (`Context.Service<X, Shape>()("key")`) and generator functions (`Effect.gen`) are erasable and are used.
- Type-only imports use `import type` (or inline `type`); Node.js does not remove unused value imports.
- Relative imports carry the `.ts` extension.
- Node.js does not type check. `npm run check` is the only type check.
- Every Effect and `@effect/platform-node` name used in the program is recorded in `docs/effect-v4-api.md` with the file and line of its declaration in `node_modules`. Look a name up there, or read the `.d.ts` file and add it, before using it. Material online describes v3 in most cases and is not a source.

## Programming principles

The program follows functional programming: pure functions everywhere except at the edges, which are
identified as such (the layers of `src/store.ts`, `src/webUi.ts`, `src/claude.ts`, `src/codex.ts`, and the
untested wiring); no exception is thrown — a failure is a typed error in the `Result` or the error
channel of an Effect, and a defect is a bug; data are immutable algebraic data types (readonly records,
tagged unions, `Result`, `Option`), never mutated after construction; recursion instead of iteration
where it is stack safe (`Effect.gen` and Effect's own combinators are, plain recursion over
unbounded input is not); effects are values, composed and run at the edge; and the rest that goes
with it: no shared mutable state, no `null`-or-throw signatures, no hidden preconditions,
exhaustiveness over variants, and a pure core that the tests exercise directly. The findings and
recommendations of `docs/functional-design-review.md` are the reference for what this means here.

A type admits exactly the values the domain has. Where the presence, meaning or legality of one field
depends on another field's value, the type is a tagged union of the cases, not a record with a flag;
fields that cannot vary independently are one field. A validation rule that rejects a *combination*
of fields is evidence that the type is wrong — make the combination unrepresentable rather than check
for it. The same holds for a check on a value's own content: a string that must not be blank, a
number within a range, a path already resolved, a text of one line. The value gets a type whose only
inhabitants satisfy the rule, built by a function that returns a `Result`, so that an invalid value
cannot be constructed rather than being rejected after it exists; `ProjectPath` and `RecordPath`
(`src/services.ts:87`) are the pattern already in use. What stays a check is what no constructor can
decide: a comparison of a value with something outside it, such as a reply against what the program
supplied, and a judgment of prose that only a reviewer can make. At the agent
boundary a union becomes an `anyOf` of closed objects in the JSON Schema, which both agents accept:
the `Block` union of issue #36 went to Codex and to Claude Code in both variants on 6 Oct 2026, the
strict one with its `$ref`s inlined, and all were accepted (see the facts below). A new union there
is therefore ordinary, and the prototype run proves it again whenever the schemas change.

## Behaviour that is decided and must not change without the developer's instruction

1. The program waits for the user only where a decision is required. No confirmation prompts elsewhere, with one exception (issue #25, 29 Sep 2026): every answer that ends the run is confirmed first. This covers End the run (`q` at a one-line prompt, `/quit` in a message, the page's button), Stop task in the page, and at the cycle limit every answer that stops the run (`0`, an empty answer, anything that is neither an offered `p` nor a count; `limitStops` in `src/input.ts`), clicked or typed. The page decides by one predicate, `endingOf` in `src/input.ts`, and opens `ConfirmEndDialog`. Only the dialog's confirming button ends the run; anything else returns to the question. The confirmation says what ends, that the records in `plan-review/` remain, and the exit code the program then returns. Ctrl+C in the server's terminal ends the server and asks nothing. An execution call that ends with work left and nothing for the user to decide (the status `continuing`, issue #154, decision Q2) is not put to the developer: the run continues it without a question (behavior 4). Since issue #181 (the developer's instruction of 19 Oct 2026 that the interruptions of an implementation run be minimized, requirements Q1, Q6 and Q7), neither is an execution phase that ends `needs_input`, `blocked` or `aborted` without a question the user answered during the call: the plan is revised from Claude Code's own account (behavior 4); and a final suite stopped by its time limit or unable to start is run again once in the whole run without a question, every later such stop asking Run the suite again or Stop the run (behavior 12).
2. The question phase, which is the whole of a refinement run (below): Claude Code proposes a question list (question, reason, proposed answers, default); Codex reviews it; the interview takes place in the web page; follow-up questions are unrestricted; Claude Code proposes the end with a summary and the user confirms; Codex reviews `requirements.md` for gaps, and accepted gaps lead to a second interview. Since the task of issues #46, #59, #34, #36, #25, #20, #19, #57 and #58 (29 Sep 2026), every question put to the user follows one statement of the rules, `QUESTION_RULES` in `src/prompts.ts`. Since the developer's instruction of 29 Oct 2026, the agreed list is discovered rather than selected: `questionListPrompt` carries `TASK_INVESTIGATION`, which tells Claude Code to understand the task and what accomplishing it requires, to work out what its success depends on, and to investigate the uncertainties and choices it finds, the task's intended outcome first and then the concerns of `TASK_CONCERNS` (23 of them, rendered by `taskConcernsText`), which are lenses for finding what matters and neither a checklist that owes a question each nor an exhaustive inventory; the investigation uses the task, the codebase, the project's documentation, the conventions the codebase follows, the practices that apply (the Twelve-Factor App, continuous delivery as Humble and Farley describe it, test-driven development as Beck describes it, none of which settles a choice by itself) and Claude Code's own judgment. Surveying the task's choices, writing a question for each and then removing those that do not qualify is refused in the prompt, since no check can see a discarded question. `whetherToAsk` is the determination of need: the user is asked only where his knowledge or decision is needed to establish what the task is to accomplish or to resolve an uncertainty or choice whose consequences Claude Code cannot responsibly carry, and that the options would lead to different plans or different work does not establish it; a default the codebase's conventions or a sound practice support is evidence that it may proceed without asking and is not conclusive, so how well the default is supported and what would follow if it were wrong are weighed, and where a wrong choice would cost the developer little to correct the supported behavior is chosen and nothing is asked. The `reason` field carries the evidence both sides need: the concern it bears on and what the task's success depends on there, each source investigated that did not settle it, and what would follow if the default were wrong, with that default's support; `default_answer` is still the label alone, so no agent schema changed. Codex's criterion raises an unnecessary question by naming the file, convention or answer that settles it, a reason that shows only that the answer would change the plan, or a supported default whose wrong-default cost the reason does not show; and `questionReviewPrompt` raises a consequential missing question, naming the concern it bears on, what leaves it open and what would go wrong without it. The first interview's follow-ups are held to the same rule (`clarificationRules` carries `questionWritingRules()`), and no Codex review reaches them (decision Q12). The writer's prompts carry `questionWritingRules()` and the reviewers' carry `questionReviewCriteria()`; `validateQuestion` in `src/question.ts` checks their mechanical part, with the validation repair turn of behavior 10. Every question entry carries a context paragraph. After the question review converges, a fresh session writes the explanations of the agreed questions' terms (`terms.json`), which Codex reviews in a loop of their own (the terms subject, ids `T-R<n>-<i>`) before the clarification; an empty agreed list skips it.    Since issue #184 (the developer's instruction of 19 Oct 2026, "a question must appear as soon as the previous one is answered", and decisions Q1 and G-R1-1 of its requirements), the first interview (the clarification) has no Claude Code call before an agreed question (`clarification` in `src/conversation.ts`). 14. Transport retry (issue #26, by the developer's instruction of 29 Sep 2026). A failure of an agent call is classified in `src/transport.ts`, the one place that inspects an SDK's failure: only positive transport evidence belonging to the failure (a dropped connection, a reset, a timeout, an HTTP 5xx: a terminal fact of the call, or evidence with no progress after it) makes it a `TransportFault`, and known permanent evidence (a 4xx, a usage or rate limit, a permanent assistant error, a stopping result subtype, including those of the SDK's own `api_retry` messages) wins; anything unrecognized is not retried, except the ending of an execution call's Claude Code process (issue #157, below). `TransportFault` is not a `RunError`. Codex turns and planning calls are retried by their callers in `src/review.ts`, execution calls inside `src/claude.ts`, which alone holds the call's session, stop and reporter; `Planner.executing` declares no `TransportFault`. Each retry waits `transportRetryDelaySeconds × 2^(k-1)` (behavior 9), is notified (`TransportRetrying`), said to the page and written to `conversation.md`, and shown on the page's activity line as a count of attempts, with a determinate indicator and the time remaining that count the wait down while the program waits (issue #63, by the developer's task of 7 Oct 2026; until then an indeterminate indicator). When the retries are exhausted the run pauses; its question names the agent and the call, and the attempts and the last fault are in its details, the fault shown literally as code (`transportDetails`; S52): Retry again (another full set, the waits starting again) or Stop, with decision support's offer; Stop halts with `AgentUnreachable`, naming the agent, the attempts and the last fault. ## User interface

Adherence to Jakob Nielsen's ten usability heuristics is a top priority for every user interface of
this program, which since issue #88 is the web page alone: visibility of system status; match between the
system and the real world; user control and freedom; consistency and standards; error prevention;
recognition rather than recall; flexibility and efficiency of use; aesthetic and minimalist design;
help users recognize, diagnose, and recover from errors; help and documentation. A design decision
about the interface is argued from these heuristics, and a review of the interface checks against them.
The visual design follows Material Design (Google's design system, m3.material.io): its components,
layout, typography, colour roles, elevation, motion and states. A component library that implements it
is a dependency and needs the developer's instruction like any other; without one, the guidelines are
followed by hand.
Where the library has no component for what the guidelines specify, a substitute may be used only if
it asserts nothing the specified component does not. A substitute that claims more — a determinate
indicator in place of an indeterminate one, a progress figure in place of a busy state, a count in
place of an estimate — is not a deviation but a different statement, and the guidelines are followed
by hand instead. A deviation recorded in `docs/ui-review.md` states what the substitute asserts, not
only that it was substituted. No test can catch this: a rendered element is asserted to be present,
never to be truthful (issues #42 and #43).

The rows of the progress rail that open (issue #115) show it before they are touched, with the row's one glyph, the mark,
in the container of M3's outlined toggle icon button. The ring asserts that the row can be opened; the filled container
that it is open and can be closed; the flat container without a ring that it is open and cannot be closed while something
inside it needs the user. None asserts anything about what the row holds. It deviates from M3's disabled toggle in one
respect: the glyph keeps its full state color rather than 38 %, because it states the row's status and an opacity is not
used to dim it (issue #109). The leading position still holds one glyph (issue #110's decision stands). Whether the ring
is seen and read as a control is covered by no test.

A run that waits for the user, or a run he watched that has ended, is announced to a user who is not looking at the page
(issue #16). The tab's title marker and the icon's badge assert that a prompt is pending, or that a run this page
watched ended while the tab was hidden and has not been seen since, and nothing more; they are always on and are not a
preference. A desktop notification asserts the same, once per prompt and once per end; it is opt-in and revocable from
the page's switch, and needs the browser's permission, asked from that switch's click alone. A sound is a separate
opt-in, off by default. Neither fires at a visible tab showing the prompt, and every tab of a run fires, since either
may be the one the user cannot see. The decision is `decide` in `web/src/notify.ts`. Since issue #120 it is taken for each of the page's two runs (S17): one notification per prompt and one per end of either run, and the title and the icon carry a waiting mark if either run waits.

The page's top level is two tabs, Refinement and Implementation, and the tab is the mode (issue #120, the developer's decision of 8 Oct 2026 in issue #120). The control is M3's primary tabs (m3-svelte's `Tabs`) under the top app bar: the two modes are destinations of equal rank within one project, each with content of its own, which is what M3 specifies primary tabs for, and both stay in view [recognition rather than recall]. A tab shows its run in progress, with its own rail, transcript and prompt, or else its items, which the server lists from the tracker on the page's request; the page never calls the tracker and no credential reaches it. An item starts its tab's run from its own text button, so selecting or scrolling through the list starts nothing [error prevention without a confirmation, which behavior 1 excludes]. A tab whose run waits for an answer carries the waiting mark in its name, drawn there in place of M3's badge, which m3-svelte's `Tabs` does not take; it asserts that that tab's run waits for an answer, and nothing more. A refusal is shown in the tab whose action it was, and a notice of no tab in the list view at every width (S20). A tab revisited asks for its items again (S15), and so does a tab whose items were loading when the connection was lost (S16). Until the user chooses a tab, the page shows the tab whose run waits or runs. A tracker that cannot be reached is a notice in the tab with Try again, not a failure of the page. The two tabs take their project from the server's directory (the developer's answer to question Q1 in the interview of 9 Oct 2026).

The question page shows the question as its heading, the choices under it, and the context and the question's attached material (an agreed question's reason under "Why You're Being Asked This", a permission's input, a pause's facts, the summary to confirm, a stop's report, a lost connection's fault, a stopped suite's runs, each under a heading of its own) as collapsed headings that expand (issue #137, the developer's instruction of 11 Oct 2026, which superseded S27): what is new when a question appears is the question and its choices [visibility of system status], and the context, usually read already, is one click away [recognition rather than recall]. The control is `Disclosure`, which the decision page's entries use too.

On the question page, the question and its first answer stay in view without the run area scrolling in windows 450 pixels high and taller, notice or not (the developer's decision at the stop of execution phase 1 of issue #120, 9 Oct 2026, when the tabs took 48 px of the window; `IN_VIEW_MIN_HEIGHT` in `web/src/layout.ts`, kept while the question page's tests use it); below 450 pixels the run area scrolls to the first answer.

The decision page holds the question, as its heading, and its option cards at its top, so they are in view when it appears; under them come the fixed choices, the answer field and Send, then the columns of advantages and disadvantages, then the collapsed headings (issue #133, the developer's instruction of 11 Oct 2026). Every control stays, and where the window cannot hold the answers and the columns the run area scrolls, clipping nothing; the columns are never lower than 15rem, ten lines, and are the tallest region at 1280 × 800, where the page does not scroll (his decision of 12 Oct 2026, "Every control stays, windows scroll", over hiding the controls under a heading or shrinking the top bar).

The "You and Interloq" panel is a dashboard (issue #22, the developer's decision of 11 Oct 2026): information has a fixed place and is replaced in place, rather than arriving as another message at the bottom. Its header is the run's item; in small type under it, each agent and its model; then one status line, prominent, current to whatever is happening, which is the activity line moved from under "Claude and Codex" and removed from there [visibility of system status]; the interview's help while it lasts; Claude Code's latest message and the question the developer answered last, with his answer, each on a surface of its own, so that Claude Code's information and the developer's are separated rather than interleaved; and a heading, closed until opened and shared across tabs, of every answer of the run in order [recognition rather than recall]. While a question or the decision page takes the column, the status line and that heading stay below it. The status line asserts what is happening now and not how long it will take; only the wait before a retry and the usage-limit wait carry a countdown. The rail owns phases, cycles and the plan's steps; the dashboard owns what is happening now. Given up, by his decision: the page's timed list of Interloq's own lines, with its times (issue #1) and phase bands (issue #15), which `conversation.md` and the rail keep; "Claude and Codex" keeps its own. Nothing moved into "Claude and Codex", so hiding it (issue #136) hides none of his answers and none of Claude Code's narration.

The Implementation tab carries the chain's control (issue #147, behavior 15): M3's switch, labeled "Start the next refined item when a run ends", and two optional outlined text fields, a number of runs and a time, both empty by default, with the moment a cutoff resolved to shown under its field in the browser's time, so a cutoff set on an earlier day is never the unexplained reason the machine is idle [visibility of system status]. A number of runs that is not a positive whole number is the field's error and is not sent [error prevention], and nothing asks a confirmation (behavior 1). It stands above the item list, and during a run at the top of the progress rail's column in both layouts, which holds no question, so the question page and the decision page keep their room and the 450-pixel rule above is untouched. Its status asserts that the mode is on or off, that a chain is going with its count, or why the last chain ended, and nothing more; no figure of cost appears in it.

Command-line behaviour follows the Command Line Interface Guidelines (clig.dev): the developer's
command `bin/ilcli` and the command line of `src/web.ts` (`src/webArgs.ts`). It

## Rules for changes

- The type first. Before the test, the data types and the signatures the change needs are written and settled: a change of behaviour states what its types become before anything else is written, and a plan's step says so in its text. The test is then written against them, and a type error naming a signature is the ordinary way it first fails. The types are not the application code the next rule speaks of; writing them is the first act of a change, not an exception to it.
- Test first, without exception. Before application code is written or changed, the test that specifies it is written, run, and seen to fail for the reason the change is meant to fix (a failed assertion, or a type error naming the signature being changed; never a missing module or a typo). Then the least code that makes it pass. A new module may first be scaffolded with its final signature and a body that does nothing useful, so that the test fails on its assertion. The observed failure is recorded in the commit message.
- Then refactor, which is the third step and not an optional one. "The least code that makes it pass" is licensed to be crude only because this step removes the crudeness: without it a change leaves behind what the green step was permitted to write. Improve the code against the Programming principles — a type that admits more values than the domain has, a check on a value's own content where a constructor returning a `Result` was called for, a function doing two things, duplication, a name that described the first version. **No test changes**: the tests of the step and the suites the change touches are re-run unchanged and must still pass, which is what makes it refactoring rather than a change of behaviour; a test that has to change is evidence that behaviour changed and belongs in a step of its own. Nothing is added that no test covers. The step's record says what was improved, or that nothing needed it.
- Property-based testing wherever it applies (issue #66). Where a function is pure and an invariant can be stated over arbitrary input, a property test with `fast-check` states it: the modules the Layout table marks pure are where they belong. Example tests remain for what properties do not cover: a specific case that once failed, a value a seam must agree on exactly, and the scenario tests required for every change of behaviour; the two are not alternatives, and a property over a pure function is no substitute for a scenario test. A property test is written first and seen to fail, like any other. Its case count is chosen so that `npm test` stays usable before every commit and in CI.
- Every change to behaviour gets a scenario test in `test/` that runs the procedure against the test layers of `test/helpers.ts` (`testLayer`, `testWiring`). `src/issueLog.ts` stays free of I/O and of Effect services so that it can be tested directly.
- Test the seams, not only the sides. Where two modules must agree on a value — a label, a format, a path, an identifier — a test asserts their agreement directly, by deriving both sides from one source in the test and comparing them. Testing each side against a literal of its own is not enough: it passes while they disagree. The same applies where one module produces text that another parses, and where a claim in a structured reply is meant to correspond to a change on disk. Two runs were lost in one day to seams of exactly this kind (issues #30 and #37), each with both sides tested and neither with a test of the agreement between them.
- A prompt that tells an agent what value to return, and the validation that checks the returned value, are written and changed together, and one test exercises both.
- `src/claude.ts` and `src/codex.ts` receive the SDKs through the `Sdk` service and are tested with `test/fakeSdk.ts`. Only `src/sdkLive.ts` (the binding), `src/trackerLive.ts` (the tracker's binding, issue #120) and `src/web.ts` (the wiring and the runner) are untested. Their text is no longer shown to the developer before it is written (his decision of 7 Oct 2026): the two hold 96 lines of wiring with no logic, the hook type checks them, and the work review reads them in the diff like every other file, while showing them cost a stop and, with it, a planning call, a review loop and a work review every time (issue #90). No scaffolding may reach a real agent: a scaffold of an adapter makes the SDK call impossible. Verify SDK option names against the type declarations in `node_modules`, not from memory.
- `src/codexExec.ts` spawns processes and is tested against real child processes (`test/codexExec.test.ts`), not the fake SDK, because the defect it exists for is an asynchronous `'error'` event on a stream, which a rejected promise does not reproduce (issue #158).
- `src/suiteExec.ts` spawns the project's whole suite and is tested against real child processes too (`test/suiteExec.test.ts`, issue #162), because what it must get right, a process group killed at the ceiling or on Stop task and a stream error that is never uncaught, is what no fake reproduces.
- Do not add a dependency without the developer's instruction. Permitted besides the two SDKs: `effect`, `@effect/platform-node`, and these devDependencies, each pinned exactly and checked by `test/deps.test.ts`: `fast-check` (property tests); for the web GUI (instructed 26 Sep 2026) `svelte` (the page), `vite` and `@sveltejs/vite-plugin-svelte` (the build), `vitest` (component tests), `jsdom` (the DOM for Vitest), `svelte-check` (type check of `.svelte` files), `@playwright/test` (end-to-end tests), `marked` and `dompurify` (Markdown rendering and sanitising in the page), `m3-svelte` (Material Design 3 components) and `vite-plugin-functions-mixins` (the CSS `@function`/`@mixin` of m3-svelte's components, resolved at build time). A runtime dependency, permitted on the developer's instruction of 28 Sep 2026: `zod` (4.6.5, the Agent SDK's peer dependency), because the SDK's `tool()` takes the input of `report_step` only as a zod shape; it is imported by `src/sdkLive.ts` alone (and by the prototype `prototypes/proto.ts`), which `test/deps.test.ts` checks with its pin. Outside npm, two tools of the container image, neither an npm dependency: bashly (generates `bin/ilcli`) and bats (its tests; permitted on the developer's instruction, 27 Sep 2026; meant to come from the image, installed by hand until then).
- This directory is the development clone. The installed program is `~/work/interloq` on the host, which project containers mount read-only at `/opt/interloq`, and it tracks the branch `release` of github.com/mackler/interloq, not `main`. A change reaches real runs by one route: the developer runs `bin/ilcli release` (pushes `main`); the workflow `.github/workflows/ci.yml` runs `npm test` and then the end-to-end tests on GitHub; only if both pass does its `release` job fast-forward `release` to that commit (with a deploy key, the only identity a ruleset lets update `release`); then `bin/ilcli upgrade` on the host brings the installed copy to `origin/release` and runs `npm ci` and `npm run build`. So the installed copy can only ever pull a commit whose suite has passed — the point of the route. Nothing in this container can push, reach GitHub Actions, or touch `~/work`; the developer does those steps.
- `bin/ilcli` starts the development container (`compose.cc.yaml`) and carries a change to the installed copy (`release`, `upgrade`); it is not part of the program. It is generated by bashly from `bin/ilcli.bashly/` and tested by `test/cli/*.bats`.

## Credentials in the development container

`CLAUDE_CODE_OAUTH_TOKEN` is Claude Code's login, and Codex's credentials come from the `~/.codex`
volume; both are needed for a run. `INTERLOQ_ISSUES_TOKEN`, added 27 Sep 2026, is optional and is
**not** used by the program: it is a fine-grained GitHub token limited to this repository with Issues
read and write, which lets the assistant working in the container file an issue with the REST API.
Reading issues needs no token, because the repository is public. No module of the program reads a
credential, with one exception: the live binding `src/trackerLive.ts` reads the tracker's credential, GitHub's or GitLab's, and passes it on,
as `src/sdkLive.ts` reads `process.env` for `inheritedEnv` (issue #78); each adapter takes its credential as a parameter. No
prompt, record or log may contain a credential; every process in the container can read the
environment, so the token's scope is the safeguard, not its secrecy.

The program's own tracker credentials (issue #120), one per tracker, since a run must work in this repository (GitHub)
and in `iou-notes` (GitLab). None is ever in a config file. A project container must receive the variable for a run to
reach its tracker; the developer arranges that.

The container receives the credentials of the shell that created it (`compose.cc.yaml` names them as bare variables), and no `bin/ilcli` command passes one at exec time (issue #124, the developer's decision of 9 Oct 2026). A credential added or changed afterwards reaches no program in the container until `bin/ilcli down` and a start, which stops Claude Code and the web server running in it. `bin/ilcli run`, `shell` and `web` never recreate a running container: from a shell whose variables differ from the creating shell's they print a note naming `bin/ilcli down` and what it stops, and change nothing. Exporting the same variables in every shell, as the developer does from `~/.config/fish/config.fish`, keeps the note from appearing; it is no longer required to keep one command from stopping another's program.

- `INTERLOQ_GITHUB_TOKEN`: a fine-grained GitHub token limited to the repositories Interloq runs in, with Issues read
  and write (labels are set through the issue endpoints) and Metadata read, which GitHub grants with it. It is separate
  from `INTERLOQ_ISSUES_TOKEN`, which belongs to the assistant in the development container and stays unused by the
  program.
- `INTERLOQ_GITLAB_TOKEN`: a project access token of `adammackler/iou-notes` alone, which the developer created on
  12 Oct 2026 on GitLab's free plan, from his key file `interloq-gitlab-token`, with the `api` scope and the Planner role
  (access level 15). The Planner role can edit issues, labels and boards; it cannot push code or read or change CI
  variables, so a leaked token reaches this one project's issues and boards. Read by `src/trackerLive.ts` alone for the
  GitLab adapter and sent in the `PRIVATE-TOKEN` header, never in a URL.

### Configuring a GitLab project (`iou-notes`)

The configuration names the project by its path and one label per state; `deployed` has none, since a closed issue is
deployed. With `INTERLOQ_GITLAB_TOKEN` set in the container:

1. Create the four labels in the project (Manage → Labels), for example `Unrefined`, `Refined`, `Implementing` and
   `Implemented`; a label's name may not contain a comma. A board with one list per label shows the states.
2. The token's access to the project, which shows `"project_access": {"access_level": 15}` for the Planner role:

```
curl -s -H "PRIVATE-TOKEN: $INTERLOQ_GITLAB_TOKEN" "https://gitlab.com/api/v4/projects/adammackler%2Fiou-notes"
```

3. `<project>/plan-review/config.json`:

```
{
  "tracker": {
    "kind": "gitlab",
    "project": "adammackler/iou-notes",
    "labels": {
      "unrefined": "Unrefined",
      "refined": "Refined",
      "implementing": "Implementing",
      "implemented": "Implemented"
    }
  }
}
```

An open issue must carry exactly one of the four labels: one with none or with two fails its read, and one with two
fails its state's listing, each naming the issue and its labels. Dragging an issue between a board's label lists swaps
its labels, which keeps that true. A closed issue is deployed and listed in no tab.
